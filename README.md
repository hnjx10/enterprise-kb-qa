# 企业智能知识问答平台（RAG）

面向企业内部制度文档的检索增强问答：文档按**标题 → 段落 → 句子**层级分块，**向量 + BM25 双路召回**，**RRF** 融合，按部门做**文档级权限过滤**，**SSE** 流式返回带引用的答案。

一个能跑的、每个数字都能自己重跑一遍的 RAG 工程实现——不是 demo，也不假装比真实系统强。

| 指标 | 实测 | 口径 |
|---|---|---|
| 语料 | 10 篇 / 55 个分块 | `data/docs`，中文制度文档（HR / 财务 / IT / 销售 / 机器人） |
| 标注集 | 78 条 | 每条标「文档 + 章节」，不标 `chunk_id` |
| Top-3 命中率 | **92.3%** | hybrid，K=5 |
| 查全率 Recall@5 | 0.9427 | hybrid（单路向量 0.9321 / 单路关键词 0.9150） |
| MRR | 0.8594 | hybrid |
| 检索耗时 | P50 **0.54 ms** | 单进程、本机、不含网络 |
| 首字 TTFT | P50 **0.71 ms** | 离线抽取式生成，不含模型与网络 |
| 缓存命中 | P50 **0.03 ms** | 进程内 LRU（本机未起 Redis） |

`kbqa eval` 与 `python benchmarks/latency.py` 各一条命令即可复现。**数字与口径写在一起**，因为脱离口径的指标没有意义。

## 数据流

```
Markdown 文档
   │  ① 解析 front matter（title / dept）
   ▼
层级分块（标题 → 段落 → 句子，section_path 同时是引用来源）
   │  chunk_id = "doc_id::0007"，确定性可复现
   ├──────────────────────┐
   ▼                      ▼
FAISS IndexFlatIP       BM25Okapi
（哈希嵌入 / 可切 Qwen）  （jieba + 领域词典 + 同义词）
   │                      │
   │ top-12 × oversample  │ top-12 × oversample
   └──────────┬───────────┘
              ▼
   ② 权限过滤（部门 + 公共文档）—— 在截断之前
              ▼
   ③ RRF 融合（k=60，只取名次）→ top-5
              ▼
   ④ 答案缓存（key = 问题 + 部门集合 + 索引指纹）
              ▼
   ⑤ SSE：meta（引用 + 检索诊断）→ token* → done
```

## 为什么这样设计

### 分块：按文档自身的结构切，长度只作兜底

固定窗口（每 500 字一刀）有两个问题都占：切太碎，一块里没有完整语义，模型拿到半句话只能猜；切太粗，一块塞三四个主题，向量被平均成一个谁都不像的方向。

这里用文档自身的结构：标题给 `section_path`（它就是引用的来源，用户能核对到「住宿费标准」而不是只看到一个文件名），段落是作者划好的语义边界，只有单段超 `max_chars`（700）时才退到句子级。

三个参数各管一件事：

- `target_chars=300`：打包目标，攒够就切
- `max_chars=700`：硬顶。只设目标不设硬顶，遇到一个 3000 字的段落照样切出一块 3000 字
- `min_chars=80`：尾巴太短并回上一块，避免切出「一、总则」这种四字块

`overlap_sentences=1` 不是「多召回一点」，是防止答案正好落在切口上——一句话被劈成两半，两块都答不完整。

### 双路召回：两路的强项不重叠

向量擅长语义相近：问「出差住宿能报多少」，能召回写「住宿费标准」的段落。但它对精确串很弱：型号 `A-2024`、条款编号「第 3.2 条」、人名，被压成稠密数字后差异被抹平。BM25 正相反：几乎不看语义，但「差旅报销」四个字出现在文档里就一定排前面。

所以在同一份标注上，单路向量 0.9321、单路关键词 0.9150，而两路融合 0.9427——不是「谁更好」，是「它们的错误不重合」。

### RRF：只取名次，不取分数

`score = Σ 1/(k + rank)`，`k=60`（论文默认）。

关键在于**不吃分数**：向量相似度是 0~1 的余弦，BM25 是无上界的实数，直接加权求和要先归一化，而归一化系数会随查询分布漂移——今天调好的 0.6/0.4，换个问法就失衡。只取名次绕开了这个标定问题，也是 RRF 几乎不需要调参的原因。

工程上的一个细节：融合后同分的块按 `chunk_id` 稳定排序。否则评测结果会随字典遍历顺序轻微抖动，同一份代码跑两遍出两个数字。

### 权限过滤：多取样 → 过滤 → 再截断

放在生成之后等于没做：模型已经看到了不该看的段落，你只能拦住输出，拦不住它「知道了什么」。

放在召回之后、截断之前同样有问题：无权限文档先占掉 top-k 名额，过滤完剩下的条目数随用户权限变化，**权限越小召回越差**。这在数据上看不出来，只有低权限用户反馈「搜不到东西」时才暴露。

所以 `oversample=4`：每路先取 `top_k × 4` 的候选，过滤后再截断到 `top_k`，被过滤掉多少条作为诊断返回。实测「年假有几天」在 `--dept hr` 下过滤掉 73 条，若不多取样，这 73 条会把真正的答案挤出候选。

### 生成：真正的兜底在生成侧，不在检索侧

这一点反直觉，但很重要：**向量检索永远返回 top-k**。一个和语料毫无关系的问题，也会拿到 5 个「最不相关」的块。指望「没召回到就不调模型」来防编造，是防不住的。

所以拒答逻辑写在生成器里：抽取式生成按词重叠挑句，**没有一句与查询有词重叠就拒答**，而不是硬凑。`tests/test_pipeline.py::test_extractive_generator_refuses_when_no_lexical_overlap` 钉的就是这条。

默认 `llm.provider="extractive"` 不是「假装有模型」：

- 它是明确的可降级路径——没有模型时，系统仍然给出**有出处、可核对**的答案
- 它就是很多制度问答产品的真实形态（HR 政策、合规条款、SOP），模型在这里的价值是改写与归纳，不是「有没有答案」
- 它让整条链路离线可跑，评测数字才能在同一台机器上复现

接通义千问只需改配置：`KBQA_LLM__PROVIDER=qwen` + `KBQA_LLM__API_KEY=...`，接口不变（OpenAI 兼容）。

**抽取式的已知短板**（不掩饰）：选句靠「重叠词数 / √句长」，因此短句占优。问「年假有几天」时，「几天」在语料里没有对应词，排序实际只靠「年假」一个信号，第一句可能来自「跨年」而不是「天数」那段。接模型后由模型归纳，这个问题才真正消失。

### SSE：先 meta 后 token

前端要的是「先看到出处，再看到答案」。先流式吐答案、最后给引用，引用就成了事后补充，用户不会回去核对。

`meta` 在检索完成时立即下发，带着 `citations` 和检索诊断（候选数、过滤数、耗时），前端可以先把「依据：《差旅与费用报销管理办法》> 住宿费标准」画出来，再往上填字。

选 SSE 不选 WebSocket：问答是单向流，双向能力用不上却要多维护心跳、重连与代理兼容。SSE 走普通 HTTP，nginx 关掉缓冲就能用（响应头里已带 `X-Accel-Buffering: no`）。

### 缓存：key 少一项就是一条泄漏

只按问题文本做 key 是**危险的错**：同一句「年终奖怎么算」，HR 问和普通员工问，答案里的数字不一样。key 必须含三项：

1. 规范化后的问题（NFKC + casefold）
2. **提问者的部门集合**
3. **索引指纹**（文档更新后旧答案必须失效）

少任何一项都会出现「A 看到 B 的答案」——它不报错，只会安静地泄密。`test_cache_key_differs_by_department` 与 `test_cache_key_differs_by_index_digest` 是两条独立的用例，因为它们对应两种不同的失效方式。

缓存的是**答案**不是检索结果：检索是毫秒级，缓存它省不了多少；生成是秒级，那才是瓶颈。缓存检索结果还要处理「命中但权限变了」的失效问题，收益小、风险大。

### 一种 SQL，两种方言

MySQL 用 `%s` 占位、SQLite 用 `?`。这里的做法是统一写 `?`，在 MySQL 分支替换成 `%s`。代价是 SQL 里不能出现字面量 `?`——这个约束很便宜，比维护两套语句便宜得多。

自增主键差异（`AUTOINCREMENT` / `AUTO_INCREMENT`）在建表语句里分支，其余 DDL 只有类型名不同。

## 检索评测

### 结果

```
$ kbqa eval --k 5
检索评测 · 78 条标注 · K=5

  模式            Recall@K     Hit@3       MRR
  vector          0.9321    0.8590    0.8090
  keyword         0.9150    0.8974    0.8594
  hybrid          0.9427    0.9231    0.8594

  双路 vs 单路向量：查全率 +1.1%，Top-3 命中率 +0.0641
```

三个指标回答三个不同的问题：

- **Recall@K**：该被召回的段落召回了多少。衡量「检索层有没有漏」，与生成质量无关
- **Hit@3**：用户最可能看的前三条里有没有正确答案。比 Recall 更贴体感——第 8 条命中了，用户不会翻到第 8 条
- **MRR**：第一个正确结果排第几位。用来发现「能召回但排序差」，这类问题在 Recall 上看不出来

### 提升幅度随 K 衰减

同一份标注、同一个索引，唯一变化的是 K：

| K | vector | keyword | hybrid | 双路 vs 单路向量 |
|---|---|---|---|---|
| 2 | 0.7996 | 0.8744 | 0.8509 | +6.4% |
| 3 | 0.8402 | 0.8765 | 0.9043 | **+7.6%** |
| 5 | 0.9321 | 0.9150 | 0.9427 | +1.1% |
| 10 | 0.9496 | 0.9171 | 0.9624 | +1.4% |

K 变大，两路各自都能兜住更多，融合的增益空间被压缩——K=10 时向量单路已经 0.9496，天花板就在 0.96 附近。**「提升了百分之多少」不说 K，等于没说。**

K=2 那一行还藏着一个反例：hybrid（0.8509）**低于**单路关键词（0.8744）。原因很直接——向量路在 K=2 时只有 0.7996，融合会把它的错误块带进前两名，挤掉 BM25 原本正确的第二条。融合不是单调变好，它在「一路明显更弱」且「名额极少」时会拖后腿。这条留在表里，不删。

### 口径说明：简历上的 18% 与本仓库的 +1.1%

简历写的是「查全率较单路向量检索提升 18%」。本仓库在同一套方法、同一份 78 条标注上复现，实测最大 +7.6%（K=3），K=5 时 +1.1%。

差距不来自方法，来自**标注集的难度分布**：

- 本仓库这 78 条问题大量沿用文档原词（「住宿费」「报销时限」），BM25 单路已经 0.9150，天花板很低
- 实习期间的内部标注集里同义改写、口语化提问更多，关键词路先掉下来，融合增益自然更大
- 融合增益本质上等于**两路错误的互补量**。两路都强（0.93 / 0.92）时，可提升空间只剩几点

所以这个仓库不把 18% 凑出来，只把能重跑的 +1.1% / +7.6% 和一张随 K 变化的表放上来。换标注集、换 K，同一条命令就能得到新数字——**能被追问的指标才是自己的**。

### Top-3 未命中的 6 条

```
q02  出差住酒店超标准了怎么办
q18  年假能不能留到明年再休
q33  忘记打卡一个月能补几次
q71  在外地住酒店的钱谁出，能报多少
q73  电脑摔坏了要赔钱吗
q77  在外地吃饭公司管吗
```

看一眼就知道是什么问题：**标注口径与问句粒度不匹配**。q18 的正确答案在「年假是否可以跨年」，但召回的是「年假天数如何计算」——两段都讲年假规则，一条问句同时像两个章节。这类问题用「文档 + 章节」当标注，本身就是二义的。

这 6 条不去调参救。为 78 条标注调参数，调到 96% 也不代表在真实问题上能到 96%。

### 这份标注集不能证明什么

78 条是自建的，覆盖 10 篇文档的主要章节，但：

- **规模太小**：78 条里 1 条命中差就差 1.3 个点，涨跌两三个点可能是噪声
- **问题太像文档原句**：没有真实用户的口语化、错别字、多轮追问
- **没有多跳问题**：「出差住宿超支了，报销和审批分别找谁」需要跨两篇文档
- **不验证生成质量**：只评检索。答案可读性、引用准确率没有自动指标

它是一个「改动前后能不能比」的横尺，不是一个「系统有多好」的结论。

## 性能

`python benchmarks/latency.py`，50 次单条问答，本机（Windows，CPU，`faiss-cpu`）：

```
  阶段            n       P50       P95      mean       max   (ms)
  检索             50      0.54      1.01      0.63      1.84
  首字 TTFT        50      0.71      5.77      1.20      7.16
  完整             50      0.74      5.80      1.23      7.19
  缓存命中           50      0.03      2.22      0.22      2.24
```

口径要说清：**不含网络、不含模型推理**。TTFT 测的是「进程内从收到问题到吐出第一个 token」，生成器是离线的抽取式，所以是亚毫秒级。接 qwen 之后 TTFT 会被模型首包主导（百毫秒量级），那才是简历里「首字 < 500ms」对应的场景——本仓库没有 API key，不写自己没测过的数字。

P95 明显高于 P50 是首轮 jieba 预热与 GC 抖动，不是检索本身的方差。

缓存命中 P50 0.03ms、P95 2.22ms：P95 那几次是进程内 LRU 恰好触发淘汰 + 重新加载索引的抖动。

## HTTP 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/healthz` | liveness，进程活着就 200 |
| GET | `/readyz` | readiness，索引没装好返回 503（附分块数 / 生成器 / 缓存后端） |
| GET | `/version` | 版本与产品名 |
| POST | `/v1/search` | 只检索不生成，返回每条的 `sources` 与两路名次 |
| POST | `/v1/ask` | SSE 流式问答 |
| GET | `/v1/documents` | 文档清单，按调用者权限过滤 |

身份从请求头来：`X-User-Id` 与 `X-Depts`（逗号分隔）。没传 `X-Depts` 时回落到 `users` 表里登记的部门；都没有则只看公共文档（`dept=""`）。

SSE 事件序列：

```
event: meta
data: {"cached": false, "citations": [...], "diagnostics": {...}, "retrieval_ms": 0.83}

event: token
data: {"text": "住宿费按城市等级"}

event: token
data: {"text": "分档，凭发票据实报销"}

event: done
data: {"cached": false, "elapsed_ms": 1.21, "chunks": 5}
```

`/readyz` 与 `/healthz` 分开是有原因的：索引缺失不该让进程起不来（容器会被反复重启），但也不该接流量。启动时索引装载失败只记 warning，由 `/readyz` 返回 503 把流量挡在外面。

客户端断开后生成循环会 `is_disconnected()` 检查并停止——继续生成只是白烧 token。

## 部署

```bash
docker build -t enterprise-kb-qa .
docker run -p 8000:8000 \
  -e KBQA_STORE__BACKEND=mysql -e KBQA_STORE__MYSQL_HOST=10.0.0.12 \
  -e KBQA_LLM__PROVIDER=qwen -e KBQA_LLM__API_KEY=sk-xxx \
  enterprise-kb-qa
```

索引在构建期生成——制度文档是低频变更的，打进镜像比每次启动重建更可控；文档更新走「重建镜像 → 滚动发布」，索引与文档版本天然一致。

`--workers 2`：索引只读可共享，但每个 worker 各持一份内存索引。再多就该把检索拆成独立服务，而不是继续加 worker。

## 配置

分层：**构造参数 > 环境变量 > `.env` > 代码默认值**。前缀 `KBQA_`，嵌套用双下划线。

```bash
# .env
KBQA_ENV=prod
KBQA_LOG_JSON=true
KBQA_RETRIEVAL__FINAL_TOP_K=5
KBQA_RETRIEVAL__OVERSAMPLE=4

# 生产：MySQL + Redis + 真实向量模型 + 真实生成模型
KBQA_STORE__BACKEND=mysql
KBQA_STORE__MYSQL_HOST=10.0.0.12
KBQA_STORE__MYSQL_PASSWORD=***
KBQA_CACHE__REDIS_URL=redis://10.0.0.13:6379/0
KBQA_EMBEDDING__PROVIDER=qwen
KBQA_EMBEDDING__API_KEY=***
KBQA_LLM__PROVIDER=qwen
KBQA_LLM__API_KEY=***
```

三个「默认值即立场」的选择：

- `embedding.provider="hashing"`：离线可跑，不依赖 API key。评测里的对比必须能在同一台机器上重跑，否则数字只是别人的数字。切真实模型只改一个配置项，接口不变
- `llm.provider="extractive"`：没有模型时也给有出处、可核对的答案，而不是沉默或胡编
- `store.backend="sqlite"`：`pip install` 之后立刻能跑，MySQL 是生产配置，两者共用一份 SQL 语义

领域词表与同义词表也是配置的一部分，可用环境变量指到别处：

```bash
KBQA_LEXICON=/etc/kbqa/lexicon.txt
KBQA_SYNONYMS=/etc/kbqa/synonyms.txt
```

| `test_pipeline.py` (18) | meta 在 token 之前、空召回不调生成器、缓存 key 三个维度各自独立、引用编号与 hits 对齐 |

## 一个被修掉的召回 bug

值得单独写出来，因为它是「不报错、只变差」的典型。

**现象**：`kbqa search "年假有几天" --dept hr` 的诊断是 `候选 向量 20 / 关键词 0`。关键词路一条都没返回。

**原因**不是 BM25 或融合，而在分词：jieba 的通用词典没有「年假」，把它切成「年」+「假」，而 `tokenize` 里有一条「单字一律丢弃」的规则（单字噪声大）。于是查询的关键词只剩下 `('几天',)`——「几天」在这个语料里根本不存在，BM25 对全部 55 个分块都算出 0 分，一路直接失效。

**影响**：双路静默退化成单路。从外部看只是「有些问题搜得不太好」，没有任何错误日志。

**修法**三处，缺一不可：

1. `data/lexicon.txt` 领域词表，`jieba.load_userdict` 载入——让「年假」成为词
2. `data/synonyms.txt` 同义词表——正文写「年休假」、问句写「年假」，两边都产出标准词
3. 单字规则加回退：过滤后若为空，退回未过滤的单字。宁可噪声大，也不要让一路返回 0 条

修完再跑：关键词路从 0 条变成 3 条，「年假天数如何计算」排到第 2；全量评测 Recall@5 从 0.9321 升到 0.9427。

这件事的教训写在这里：**检索系统的失败大多是静默的**。所以 `search` 命令要打印每一路的候选数与名次，`doctor` 要检查两份数据是否同步——不是为了让输出好看，是因为不打印就永远发现不了。

**关于 LangChain**：简历技术栈里写了它。本仓库这条链路是手写的，原因写在代码里也说得清——三处都要改框架的默认行为：分块要在标题栈上维护 `section_path`（`TextSplitter.split` 只回文本，结构丢了），RRF 要知道每一路的名次（`EnsembleRetriever` 默认按加权分数融合），权限过滤必须发生在「召回后、截断前」（框架的 retriever 没有这个钩子）。三处都要绕过框架，直接写更便宜——这条链一共一千二百行左右。原型阶段用过 `DocumentLoader + TextSplitter + FAISS`，换掉是为了控制边界，不是为了不用框架。

## 已知限制

- **嵌入是哈希的，不是语义的**。`HashingEmbedder` 用 blake2b 把词映射到 512 维并 L2 归一化，能跑通全链路、能复现评测，但它抓不到「住宿」与「酒店」的同义关系。这是为了让仓库零依赖可跑而付的代价，换成 `qwen` 只需要一个配置项
- **抽取式生成不改写**。它把原文句子摘出来，所以读起来是「原文拼接」而不是「一段连贯的话」。数量型问句（「几天」）的选句排序不理想，因为只有一个词可用
- **没有多轮上下文**。`/v1/ask` 接收 `history` 并传给模型，但抽取式生成器会忽略它。检索也不做 query rewrite，追问「那超出的部分呢」会被当成独立问题
- **评测只覆盖检索**。生成质量（答案可读性、引用准确率）没有自动指标，只有人工抽查
- **索引是单机文件**。`faiss-cpu` + 本地文件，多实例部署时各自持有一份，更新索引需要滚动重启。生产上要么放共享存储 + 版本化目录，要么上独立检索服务
- **MySQL 分支没有 CI**。本地是用 SQLite 跑通的，MySQL 的方言替换（`?` → `%s`）有单元测试但没在真实 MySQL 上跑过
- **没有重排（rerank）**。RRF 之后直接截断到 top-5。加一个 cross-encoder 重排通常能再涨几个点，但会引入模型依赖，与「离线可复现」冲突，所以没做
